# Brief: block-parser

> 2026-11-27 改訂：`syntax-tree` を「行 × 帯」と「中身の上の CST」のモデルで作り直した（入力資料は `INPUT.md`、契約は `syntax-tree` の design、`include/amark/` の公開ヘッダ、`syntax-tree` の tasks.md の Implementation Notes）。`html-renderer` も同じモデルで作り直した（承認済み）。この brief から requirements、design、tasks を作り直す。前の版（2026-11-26 承認、ソースの絶対位置の構文トークンと編集の追跡のモデル）の requirements、design、research、tasks は引き継がない。

## Problem
Markdown のテキストから構文木を作るには、まずブロック構造（引用、リスト、コードブロック、見出し、段落など）を確定させる必要がある。Amark では、CommonMark のブロック構文も、利用者の拡張と同じ公開 API の上に乗せる。そのため、個別の構文の知識を持たない汎用のブロック構文エンジンと、拡張から使えるブロック構文 API が要る。

さらに、パーサは元の表記を `syntax-tree` の配置の層に記録しなければならない。無編集の往復でバイト単位で同じ出力を得ること、msgstr を差し込んでもコンテナの構造と訳していない部分の表記を保つことは、この記録が正しく、過不足ないことに懸かっている。

## Current State
- `block-parser` の実装はない（`src/parse/`、`src/syntax/` のパースの部分、`include/amark/scan.h`、`parser.h`、`block.h`、`commonmark.h` はまだない）。
- 前の版の spec は、旧モデルの API の上で書かれていた。構文トークン（`token.h`、ソースの絶対位置）、`amark_document_check_tokens`、`CONTAINER_PREFIX` と `PARTIAL_TAB` と `LAZY_CONTINUATION` の印、編集の追跡、リテラルのモード、インラインへの「区間の並び」、自前のラベルの正規化と定義の表を使っていた。これらはもうない。
- 今の `syntax-tree` が提供するもの：
  - 文書の行の表。ソースの逐次の追加（`amark_document_add_source` / `_append_source` / `_finish_source`）、改行の種類、BOM のソースの印、列とバイトの対応（タブは 4 列のタブストップ）。
  - 配置の記録：ブロックの行の範囲、コンテナの帯（`present` / `lazy`、項目の最初の行の `first`）、空行、葉自身の表記（レイアウトのトークン）、中身の部分。段落の行を別の葉へ移す操作、行を取り除く操作、中身の先頭を表記に変える操作。
  - 綴りの記録：中身の上のトークン（9 種類）。値は綴りから導く。記録は編集ではない（`amark_node_record_*`）。
  - 定義の索引：`link_definition` のノードが木にあれば、参照の解決は自動で行われる。ラベルの正規化（`amark_label_normalize`）と case fold、文字参照の解読は `syntax-tree` と `src/base` にある。
  - ロスレス性の検証（`amark_document_check_lossless`：行ごとの分割と中身の被覆）。
  - リストのタイトは空行から導く。記録すると上書きの値になる。
- `html-renderer` は、組み込みのノード型の HTML の出力を構文拡張 `amark.core.html` として提供し、CommonMark の構文セットの構築関数（この spec が所有）が `amark.core` の直後に足すことを求めている。テスト専用の GFM 相当の HTML の部品 `amark_test_html_gfm` が、検証用のノード型（`test.table` など）を登録する。

## Desired Outcome
- パーサの公開 API がある：構文セットとオプションの指定、文字列全体のパース、逐次の入力（feed してから finish する）、ブロックの断片とインラインの断片のパース。
- CommonMark の行単位のブロック解析（開いているコンテナとの照合、新しいブロックの開始、遅延継続、ブロックの閉鎖）を、構文の知識を持たない汎用のエンジンとして実装する。
- 公開のブロック構文 API で、開始と継続の条件、段落の中断、行の受け入れ、閉じる処理、段落の先頭の行の消費、開いている段落の解釈し直しを定義でき、帯と葉自身の表記と中身を行と列で記録できる。拡張の実装者は、ソースのオフセットを計算しない。
- 文書の後処理（インラインの前と後）と、パースの間の拡張の状態を持てる。
- CommonMark 0.31.2 の全ブロック構文とリンク参照定義を、構文ごとの組み込み拡張として実装する。各構文は style（フェンスの文字、見出しの書き方など）を記録する。リストのタイトは記録せず、空行から導かせる。
- パースした文書は、インラインのエンジンが中身を覆っていれば、ロスレス性の検証に通る。コンテナの帯、遅延継続、空行、部分的なタブ、改行の種類、NUL と不正な UTF-8、BOM を、特例なしに `syntax-tree` の記録で表す。
- インラインの解析は、葉の中身（配置済み）を単位に委譲する。委譲先がなくても、テキストと改行のノードで中身を覆う既定の委譲先がある。
- 断片のパース：ブロックの断片は自分の行の表を持つ部分木として作って取り込み、インラインの断片は自由な中身として葉の中身を置き換える。

## Approach
- 構文定義駆動のエンジンとする。エンジンは、構文セットに登録されたブロック構文のスロットを優先度の順に試すだけで、個別の構文を知らない。空行と遅延継続の扱いは、どの構文にも共通なのでエンジンが持つ。
- 入力の前処理はしない。行への分割は `syntax-tree` の行の表に任せ、バイトは書き換えない。タブは列で数え、1 つのタブを帯と表記と中身で分けるときは列の範囲で分ける。NUL と不正な UTF-8 は、中身の `replaced` のトークン（項目を綴るレイアウトのトークンでは `replaced`）で綴る。
- 記録は `syntax-tree` の公開 API だけで行う。帯と空行は、その行の持ち主が決まってから記録する（空行が末尾の空行かどうかは、次の行を見るまでわからない）。
- リスト項目の空行は cmark の順で扱う（先に字下げが項目の幅に足りるかを調べる）。タイトは空行の持ち主の規則から導かれる値に任せる。
- 定義の表とラベルの正規化は持たない。リンク参照定義は `link_definition` の葉として木に置き、解決は `syntax-tree` の索引に任せる。
- パースの深さと計算量に上限を設け、病的な入力でも入力の大きさに線形になることを、計算量のカウンタのテスト、ファジング、ベンチマークで確かめる。

## Scope
- **In**：
  - パーサの公開 API、オプション、CommonMark の構文セットの構築
  - ブロック構文エンジン、公開ブロック構文 API、文書の後処理、パースの間の拡張の状態
  - CommonMark の全ブロック構文とリンク参照定義の組み込み拡張と、その style の記録
  - 配置と綴りの記録（帯、空行、葉自身の表記、中身、コードブロックと HTML ブロックとリンク参照定義の中身のトークン）
  - インラインへの委譲の取り決めと既定の委譲先
  - 断片のパース（ブロック、インライン）
  - 下流と共有する走査の関数（HTML ブロックの条件と HTML のタグ、リンクのラベル・宛先・タイトル、値の綴りの単位）
  - ブロックの GFM 相当の検証用の部品（表、脚注の定義、タスクリスト）、テストの補助と共有の生成手順、ファジング、ベンチマーク
- **Out**：
  - インラインの解析と区切り文字の処理（`inline-parser`）
  - CommonMark spec の全例での HTML 出力の 100% の判定（`inline-parser`）。この spec では、木のダンプでの照合と、spec のブロックの章の例で検証する。
  - HTML と Markdown の出力（`html-renderer`、`markdown-renderer`）

## Boundary Candidates
- ブロック構文エンジンと、パースの文脈（汎用）
- CommonMark のブロック構文の定義（組み込み拡張）
- 記録の規約（構文ごとに、どの列を帯・表記・中身・空行にするか）
- 共有の走査の関数

## Out of Boundary
- インライン構文、区切り文字の処理
- レンダリング、帯と表記の合成、エスケープ
- 記録の形と検査、値の導出、定義の索引、タイトの導出（`syntax-tree`）

## Upstream / Downstream
- **Upstream**：`syntax-tree`（`node.h`、`document.h`、`value.h`、`spelling.h`、`dump.h`、`extension.h`、`src/base` の case fold と文字参照）、`html-renderer`（`amark.core.html`、`amark_test_html_gfm`）、`foundation`
- **Downstream**：`inline-parser`（委譲の取り決め、パースの文脈、走査の関数、検証の部品とテストの補助を使う）、`markdown-renderer`（記録の規約と HTML ブロックの条件を使う。構文セットの構築に `amark.core.markdown` を足す）、利用者の拡張

## Existing Spec Touchpoints
- **Extends**：`syntax-tree` が割り当てたスロットの種類の番号 1–4（BLOCK_SYNTAX、PARAGRAPH_CONSUMER、POSTPROCESS、PARSE_STATE）の中身を定める。
- **Adjacent**：`inline-parser`（中身の上でインラインを解析し、記録する）、`markdown-renderer`（記録を読んで書き戻す）、`html-renderer`（構文セットの構成と検証用のノード型）

## Constraints
- 次の GFM 相当のフックが、拡張だけで実装できなければならない。
  - 表：段落の最後の行を後から解釈し直すことと、行単位の継続。セルは同じ行を分け合う（`AMARK_NODE_TYPE_SHARE_LINES`）。
  - 脚注の定義：独自のコンテナと、拡張が持つ定義の表
  - タスクリスト：インラインの前の後処理で、リスト項目の結果を書き換える
- 入力は UTF-8 とする。不正なバイト列があってもクラッシュせず、処理を続ける。
- 記録は `syntax-tree` の順序の規則（帯と空行は行の順に 1 行に 1 つ、表記は行と列の順）と、記録の検査（タブ以外の文字の途中に境界を置かない、項目を綴るトークンの種類とバイトの一致）に従う。
- 中身のトークンの記録は、構造を組み立ててから行う（`syntax-tree` の葉の覚えは構造の世代ごとに有効）。
