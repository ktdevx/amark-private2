# Brief: markdown-renderer

## Problem
利用者は、Markdown をパースして木を編集し（例えば、翻訳のためにテキストを置換し）、Markdown に書き戻したい。そのとき、次の 3 つを満たす必要がある。
- 編集していない部分は、元の表記のまま残る。
- 編集した部分は、編集後の木と同じ意味を持つ、正しい Markdown として出力される。
- 無編集なら、元の入力とバイト単位で同じ出力になる。

ナイーブに出力すると、編集した木と違う意味の Markdown になってしまう。例えば、次のような問題が起きる。
- テキスト中の記号が構文として解釈される。
- 区切り文字の左右の条件（flanking）が崩れて、強調が成立しなくなる。
- コンテナ（引用やリスト）の中で、構造が崩れる。

## Current State
まだ存在しない。`syntax-tree` の構文トークンと編集の追跡、そしてパーサ（`block-parser`、`inline-parser`）が記録する構文トークンの上に作る。

## Desired Outcome
- `amark_render_markdown(node, options, ...)` 相当の API で、木を Markdown に書き戻せる。
- **往復の保証（必須）**：無編集の木を書き戻すと、入力とバイト単位で同じ出力になる。
- **意味の保存（必須）**：編集した木を書き戻して再パースすると、編集後の木と意味的に等しい木になる。表現できない木の場合は、黙って違う意味の出力を作るのではなく、エラーなどで知らせる。
- **局所性（必須）**：出力の変化は、編集したノードとその周辺に限る。編集していない部分の表記は変えない。
- 構文トークンを持たないノード（新しく作ったノード）も、正しい Markdown として出力できる。
- 拡張ノードも、上の保証に参加できる。

## Approach
書き戻しの基本的な形は「編集していない部分は元の表記を出し、編集した部分は作り直す」とする。作り直しの詳細は design で決める。少なくとも次の論点を扱う。
- **エスケープの方式**：どの文字を、どの文脈でエスケープするか。最初は保守的な方式で始め、後で必要最小限のエスケープへ改善する、という段階的な方針も選べる。
- **区切りの選び直し**：元のマーカーがその位置で使えない場合のマーカーの切り替え、区切り文字の内側の端の空白の扱い、コードスパンやフェンスの長さ、リンク先の書き方など。
- **コンテナの接頭辞の付け直し**：引用の `> ` やリストのインデント
- **周りの表記との一貫性**：元の表記（マーカー文字、インデント幅、改行コード）にどこまで合わせるか。正規化した形との使い分け。
- **拡張のスロット**：拡張が上の論点に参加するためのインタフェース。例えば、特別な意味を持つ記号の宣言や、ノード型ごとの出力処理。

どの方式を選んでも、意味の保存は、出力を再パースして木を比較するプロパティテストで検証する。この検証を受け入れ基準とする。

## Scope
- **In**：
  - Markdown レンダラの本体
  - 出力のオプション（新しいノードのスタイルなど）
  - Markdown 出力のスロットのインタフェース
  - CommonMark の全ノードの Markdown 出力
  - 往復と意味の保存のプロパティテスト
  - テスト専用の検証用拡張（GFM 相当）の Markdown 出力に対応すること
- **Out**：
  - フォーマッタとしての整形機能（編集していない部分を書き換えること）
  - パースの処理

## Boundary Candidates
- 元のまま出すか作り直すかの判定と、元の表記の出力
- 作り直し（エスケープと区切りの選び直し）
- 新しいノードのスタイル

## Out of Boundary
- パース。ただし、Markdown の断片をパースして木に差し込む編集 API が必要になった場合、その担当はパーサ側か `syntax-tree` 側かを design で決める。
- HTML 出力
- 構文トークンのモデルの定義（`syntax-tree`）。ただし、不足が見つかったら `syntax-tree` とパーサの spec に戻って補う。

## Upstream / Downstream
- **Upstream**：`syntax-tree`、`block-parser`、`inline-parser`
- **Downstream**：利用者（翻訳などの編集ツール）

## Existing Spec Touchpoints
- **Extends**：`syntax-tree` の拡張記述子に、Markdown 出力のスロットを足す。テスト専用の検証用拡張（`inline-parser` が持つ）に、Markdown 出力を足す。
- **Adjacent**：`html-renderer`（レンダラのスロットの設計は揃える）

## Constraints
- 無編集の往復でバイト単位で同じ出力になることは必須である。次の入力でも成り立たなければならない。
  - タブ、CRLF、末尾の空白
  - 遅延継続行
  - NUL 文字や BOM を含む入力
- 初期の実装で選んだ方式（例えば保守的なエスケープ）が、後で別の方式（必要最小限のエスケープ、周りの表記に合わせる出力など）へ改善することを妨げないように、公開 API とスロットを設計する。
- この spec の design で構文トークンに不足が見つかることを想定し、`syntax-tree`、`block-parser`、`inline-parser` に戻って直すことを許容する。
