# Requirements Document

## Project Description (Input)
ブロック構造が確定した後、段落や見出しの中身を、強調、リンク、コードスパン、オートリンク、生の HTML などのインライン要素として解析するインライン構文エンジンと公開インライン構文 API を提供する。CommonMark の区切り文字の処理とブラケットの処理を汎用化し、拡張（新しい区切り文字、きっかけの文字がない構文、ブラケットの後処理）が同じ仕組みに乗れるようにする。CommonMark の全インライン構文を公開 API だけを使う組み込み拡張として実装し、インラインの綴りを葉の中身の上の位置のトークンで過不足なく記録する。CommonMark spec の全例の準拠テストと、GFM 相当をテストの中にだけ置く検証用拡張で表現できることの検証、ファジングと計算量のテストを持つ。

2026-11-27 に、`syntax-tree` の新しいモデル（「行 × 帯」と「中身の上の CST」、値と style と綴りの区別、定義の索引、ロスレス性の検証、元の表記の判定）と、改訂した `block-parser` と `html-renderer` に合わせて作り直した。前の版（構文トークンと編集の追跡のモデル）の要件は引き継がない。入力は `brief.md` である。

## Introduction
Amark は、Markdown テキストと構文木を相互変換する C99 ライブラリである。`inline-parser` は、`block-parser` がブロック構造を確定させた後に、段落、見出し、拡張のブロック（表のセルなど）の葉の中身を、インライン要素として解析する。

Amark では CommonMark の構文も、利用者の拡張と同じ公開 API の上に「組み込み拡張」として乗せる。そのため、この spec は個別の構文の知識を持たない汎用のインライン構文エンジンと、拡張から使える公開のインライン構文 API を提供し、その上に CommonMark の全インライン構文を実装する。

インラインの解析は、葉の中身の上の綴りの層を作る。中身のすべてのバイトを、どのノードの何の表記かがわかるトークンでちょうど 1 回ずつ覆い、意味の値はトークンから導かせ、表記の区別は style として記録する。参照の形のリンクは、ラベルと形だけを持ち、宛先とタイトルは文書の定義の索引で解決させる。

この spec は、プロジェクト全体の受け入れゲートでもある。CommonMark spec 0.31.2 の全例を HTML 出力で照合し、あわせてロスレス性と元の表記の判定を確かめる準拠テストと、GFM 相当の構文をテストの中にだけ置く検証用拡張の組み合わせで表現できることの検証を持つ。

現在、`foundation`、`syntax-tree`（実装済み）、`html-renderer`、`block-parser` の spec がある。インラインの解析はまだなく、`block-parser` の単純な委譲先（中身の各行をテキストに、行の間をソフトブレークにする）だけがある。

## Boundary Context
- **In scope**：
  - 汎用のインライン構文エンジン（位置ごとの構文の試行、テキストのまとめ、区切り文字のスタックとブラケットのスタックの処理、きっかけの文字のない構文の適用、綴りの記録）
  - 公開のインライン構文 API（きっかけの文字を持つ構文、区切り文字の種類、ブラケットの後処理、きっかけの文字を持たない構文、ノード型の性質、エスケープに関わる文字の宣言）
  - 既定の委譲先をこのエンジンにすること、CommonMark の構文セットにインライン構文を含めること
  - CommonMark の全インライン構文の組み込み拡張と、その記録の規約（トークンの種類、項目、役割の番号、style）の公開
  - 書き戻しが使う純粋な判定の関数（区切り文字の開閉と照合、生の HTML）
  - 自由な中身（インラインの断片）の解析と、msgstr の差し込みの流れの検証
  - CommonMark spec の準拠テスト一式、テスト専用の GFM 相当の検証用拡張（インライン側の部品）と、その組み合わせの検証
  - インラインの限度、計算量、ファジング、ベンチマーク
- **Out of scope**：
  - ブロック構造の解析、インラインへの委譲の取り決めそのもの、断片のパースの入口（`block-parser`）
  - 記録の形と検査、値の導出、定義の索引、ラベルの正規化、ロスレス性の検証、元の表記の判定（`syntax-tree`）
  - HTML 出力の規則（`html-renderer`）。準拠テストで HTML 出力の不具合が見つかったら `html-renderer` を直す
  - Markdown への書き戻しと、エスケープの方式の決定（`markdown-renderer`）
  - GFM の配布と、GFM spec への公式な準拠の主張
- **Adjacent expectations**：
  - `syntax-tree` は、中身、中身のトークンの記録とその検査、値の導出、定義の索引、ロスレス性の検証、元の表記の判定を提供する。この spec はそれらを自前で持たない。不足が見つかったら `syntax-tree` に戻って更新する。
  - `block-parser` は、委譲の取り決め、パースの文脈（定義の検索、拡張の状態）、インラインの断片のパース、走査の関数、CommonMark の構文セットの構築関数、テストの補助と共有の生成手順、ブロックの GFM 相当の検証用の部品を提供する。この spec はそれらを使い、同じものを作らない。
  - `html-renderer` は、組み込みのノード型の HTML 出力と、GFM 相当の HTML の検証用の部品（検証用のノード型の登録を含む）を提供する。この spec のインライン側の部品は、そのノード型を参照するだけで登録しない。
  - `markdown-renderer` は、この spec が記録した綴り、公開した役割の番号、宣言された文字、純粋な判定の関数を使って書き戻す。同じ規則を重複して実装しない。

## Requirements

### Requirement 1: インラインの解析の入口
**Objective:** As a Amark を組み込むアプリケーションの開発者, I want CommonMark の構文セットでパースすると、段落や見出しの中身がインライン要素として解析された木が得られること, so that 構文木を意味の単位で参照・編集・出力できる

#### Acceptance Criteria
1. When 利用者がインラインの委譲先を指定せずにパースする, the Amark Inline Parser shall インラインを受け入れる中身を持つ各葉の中身を、構文セットのインライン構文に従って解析し、得たインラインのノードをその葉の子にする
2. The Amark Inline Parser shall このエンジンを、委譲の取り決めの形の公開の委譲先として提供し、`block-parser` の単純な委譲先も引き続き明示して選べるようにする
3. The Amark Inline Parser shall 葉の中身が配置済み（行を仮想の改行でつないだもの）でも自由（改行が LF のバイト列）でも、同じバイト列の中身から同じ形の木と同じトークンを作る（配置済みの中身だけが持つタブの残りの空白を、タブの残りのトークンにすることを除く）
4. The Amark Inline Parser shall 中身の外（帯、葉自身の表記、行の表）を読まず、葉の中身のバイト列とパースの文脈だけから解析する
5. When 利用者が入力を任意の位置で区切って逐次に与える, the Amark Inline Parser shall 一括のパースと同じ木と同じトークンを作る
6. If インライン構文の処理が失敗を返すか、確保が失敗する, then the Amark Inline Parser shall 解析を止めてそのエラーコードを返し、リークしない
7. The Amark Inline Parser shall `foundation` のアロケータの設定のほかにグローバルな可変状態を持たず、1 つの凍結した構文セットを、別々のスレッドの複数のパースで共有できるようにする

### Requirement 2: 汎用のインライン構文エンジン
**Objective:** As a 拡張の実装者, I want インラインのエンジンが個別の構文の知識を持たず、構文セットに登録された構文だけで動くこと, so that 組み込みの構文と同じ立場で構文を追加・削除・置換できる

#### Acceptance Criteria
1. The Amark Inline Parser shall 中身を先頭から順に調べ、各位置で、その位置の文字に反応する構文を、指定された優先度の順（同じ優先度なら構文セットの順）に試し、最初に成立した構文に、その構文が消費した範囲を任せる
2. The Amark Inline Parser shall どの構文にも消費されなかった範囲をテキストとして扱い、隣り合うテキストを 1 つのテキストのノードにまとめ、空のテキストのノードを作らない
3. When 構文セットから組み込みの構文の拡張を取り除く, the Amark Inline Parser shall その構文が反応していた文字をテキストとして扱い、他の構文の振る舞いを変えない
4. If どの構文も改行を消費しない, then the Amark Inline Parser shall その改行をソフトブレークのノードとし、中身の被覆を保つ
5. The Amark Inline Parser shall 中身の先頭と末尾の空白（空白、タブ、改行）を、葉自身の構造の綴りとして記録し、インラインのノードに含めない
6. If 構文の処理が成立しないと答えたのにノードを出したか、成立したと答えたのに範囲を出さなかったか、出した範囲がトークンで覆われていない, then the Amark Inline Parser shall 状態の誤りとして解析を止める
7. The Amark Inline Parser shall エンジンが個別の構文の名前や文字を前提にせず、構文の性質をすべて公開 API の登録から得るようにする（中身の先頭と末尾の空白と、どの構文も消費しない改行の扱いを除く）

### Requirement 3: きっかけの文字を持つインライン構文
**Objective:** As a 拡張の実装者, I want 特定の文字で始まるインライン構文を、公開 API だけで定義して登録できること, so that コードスパンやオートリンクのような構文を組み込みと同じ方法で書ける

#### Acceptance Criteria
1. The Amark Inline Parser shall 拡張が、反応する ASCII の文字の集合、優先度、その位置で構文が成立するかを判定して成立すれば範囲を消費する処理を持つインライン構文を定義して登録できるようにする
2. The Amark Inline Parser shall 構文の処理が、中身のバイト列、現在の位置、前後の文字（Unicode の空白と句読点の判定に使える符号位置）、中身の単位（テキスト、置き換え、改行、タブの残り、エスケープ、文字参照）を参照できるようにする
3. The Amark Inline Parser shall 構文の処理が、組み込みと拡張のどのインラインのノード型のノードでも作り、その部分木を組み、中身の上の範囲にトークンを付け、値と style を記録できるようにする
4. The Amark Inline Parser shall 構文の処理が、消費した範囲をテキストの一部（エスケープや文字参照の単位を含む）として出せるようにする
5. The Amark Inline Parser shall 構文の処理が、成立しないときに、続く範囲をテキストとして扱わせ、同じ範囲を何度も調べさせないようにできるようにする
6. The Amark Inline Parser shall 構文の処理が、直前のテキストの末尾の空白を取り込み、自分の範囲の綴りにできるようにする
7. The Amark Inline Parser shall 構文の処理が、パースの文脈（文書、オプション、定義の検索、パースの間の拡張の状態）を参照できるようにする

### Requirement 4: きっかけの文字を持たないインライン構文
**Objective:** As a 拡張の実装者, I want 拡張オートリンクのように特定の開始の文字を持たない構文を、公開 API だけで定義できること, so that テキストの中の語やパターンからノードを作れる

#### Acceptance Criteria
1. Where 拡張がきっかけの文字を持たないインライン構文を定義する, the Amark Inline Parser shall 強調とリンクの組み立てが終わった後のテキスト（強調の中のテキストを含む）を、その構文に調べさせ、範囲の一部を構文のノードに置き換えられるようにする
2. The Amark Inline Parser shall きっかけの文字を持たない構文が、調べる範囲の前後の中身（範囲の外を含む）と、その範囲がリンクの性質を持つノードの中にあるかを参照できるようにする
3. The Amark Inline Parser shall きっかけの文字を持たない構文に、テキストの単位だけからなる範囲を渡し、エスケープ、文字参照、置き換えたバイト、タブの残りを含む範囲をノードに置き換えさせない
4. When きっかけの文字を持たない構文がテキストの一部をノードに置き換える, the Amark Inline Parser shall 残りのテキストと新しいノードのトークンが、元のバイトを抜けも重なりもなく覆うようにする
5. The Amark Inline Parser shall 使われずに残った区切り文字とブラケットのテキストを、きっかけの文字を持たない構文に渡さない

### Requirement 5: 区切り文字の種類と規則
**Objective:** As a 拡張の実装者, I want `*` と `_` に加えて、新しい区切り文字（取り消し線の `~` など）を、開く・閉じるの判定、長さの一致の規則、作るノードとともに登録できること, so that 強調と同じ仕組みで新しいインライン要素を定義できる

#### Acceptance Criteria
1. The Amark Inline Parser shall 拡張が、区切り文字の文字、開く・閉じるの判定の規則、開きと閉じの長さの一致の規則、区切り文字の並びとして扱う長さの範囲、一致した長さごとに作るノードを持つ区切り文字の種類を登録できるようにする
2. The Amark Inline Parser shall すべての区切り文字の種類を、CommonMark の区切り文字の処理（左右の flanking、`_` の語の中の規則、長さの和が 3 の倍数になる場合の規則、下限の扱い）と同じ手順で、1 つの区切り文字のスタックの上で処理する
3. The Amark Inline Parser shall 異なる文字の区切り文字どうしを一致させない
4. When 区切り文字の開きと閉じが一致する, the Amark Inline Parser shall 間のノードを子とするノードを作り、使った区切り文字の各文字をそのノードの区切り文字のトークン（開きと閉じを区別する役割つき）として記録する
5. When 区切り文字の並びが一致しないか一部だけが使われる, the Amark Inline Parser shall 残った文字を、区切り文字のトークンと記録した literal を持つテキストのノードとして残し、隣のテキストと 1 つにしない
6. The Amark Inline Parser shall 開くことも閉じることもできない区切り文字の並びを、通常のテキストとして扱う
7. The Amark Inline Parser shall 組み込みの強調と強い強調も、この区切り文字の種類の登録だけで実装する
8. The Amark Inline Parser shall 区切り文字の並びの開く・閉じるの判定と、区切り文字の並びの列の照合を、パースの文脈なしで使える公開の関数として提供し、エンジン自身も同じ規則で判定と照合を行う

### Requirement 6: ブラケットとその後処理
**Objective:** As a 拡張の実装者, I want `[` と `![` で始まり `]` で閉じる範囲の解釈（リンク、画像、脚注の参照など）を、ブラケットの後処理として登録できること, so that リンクと同じ仕組みで新しいブラケットの構文を定義できる

#### Acceptance Criteria
1. The Amark Inline Parser shall ブラケットの開きを 1 つのブラケットのスタックで扱い、閉じのブラケットが現れたとき、その開きの種類（`[` か `![`）を扱うブラケットの後処理を優先度の順に試して、最初に成立したものにノードを作らせる
2. The Amark Inline Parser shall ブラケットの後処理が、開きの範囲、ブラケットの中の範囲、閉じのブラケットの後の中身、開きの後に別のブラケットが開いたかを参照し、閉じのブラケットの後の範囲を消費できるようにする
3. When ブラケットの後処理がノードで中身を包む, the Amark Inline Parser shall ブラケットの中の区切り文字を先に処理し、ブラケットの中のノードを新しいノードの子にする
4. When ブラケットの後処理がブラケット全体を子を持たないノードに置き換える, the Amark Inline Parser shall ブラケットの中の解析の結果を捨て、開きから消費の終わりまでをそのノードのトークンで覆わせる
5. When リンクの性質を持つノード型のノードをブラケットの後処理が作る, the Amark Inline Parser shall それより前の `[` の開きを無効にし、リンクの中にリンクができないようにする
6. If どのブラケットの後処理も成立しないか、開きが無効である, then the Amark Inline Parser shall 開きを、区切り文字のトークンと記録した literal を持つテキストのノードとして残し、閉じのブラケットをテキストとして扱う
7. The Amark Inline Parser shall ブラケットの後処理が参照の形のリンクの成否を、パースの文脈の定義の検索（断片で挿入先の定義を使う場合を含む）で判断できるようにし、自前の定義の表を持たない

### Requirement 7: CommonMark のインライン構文の組み込み拡張
**Objective:** As a Amark の利用者, I want CommonMark のすべてのインライン構文が、構文ごとの組み込み拡張として提供され、CommonMark の構文セットに含まれること, so that 追加の設定なしに CommonMark を解析でき、構文ごとに無効化や置き換えもできる

#### Acceptance Criteria
1. The Amark Inline Parser shall CommonMark spec 0.31.2 のすべてのインライン構文（バックスラッシュのエスケープ、実体参照と数値文字参照、コードスパン、強調と強い強調、リンク（インライン、完全参照、省略参照、ショートカット参照）、画像、オートリンク（URI とメールアドレス）、生の HTML、ハードブレーク、ソフトブレーク、テキスト）を組み込み拡張として実装する
2. The Amark Inline Parser shall 各インライン構文を、名前で取り除いたり置き換えたりできる構文ごとの拡張として提供する
3. When 利用者が CommonMark の構文セットを作る手段を使う, the Amark Inline Parser shall ブロックの構文の拡張に加えて、すべてのインライン構文の拡張をその構文セットに含める
4. The Amark Inline Parser shall テキスト、コードスパン、生の HTML のノードの値と、インラインの形のリンクと画像の宛先とタイトルを、CommonMark の規則どおり（エスケープと文字参照の解読、コードスパンの改行と前後の空白の扱いを含む）に、記録したトークンから導かれるようにする
5. The Amark Inline Parser shall オートリンクの宛先を、CommonMark の規則どおり（メールアドレスの `mailto:` を含む）の値として記録する
6. The Amark Inline Parser shall 組み込みのインライン構文を、利用者の拡張と同じ公開 API だけで実装する
7. The Amark Inline Parser shall 構文の間の優先の規則（コードスパン、オートリンク、生の HTML が強調やリンクより強く結びつくこと）を CommonMark spec のとおりに満たす
8. The Amark Inline Parser shall バイト列の先頭が 1 つの生の HTML（開始タグ、終了タグ、コメント、処理命令、宣言、CDATA）であるかを、パースの文脈なしで判定する公開の関数を提供し、組み込みの生の HTML の構文と同じ規則で判定する。開始タグと終了タグの規則は `block-parser` の走査を使い、重複して実装しない

### Requirement 8: インラインの綴りの記録
**Objective:** As a `markdown-renderer` の開発者, I want インラインの元の表記が、どのノードの何の表記かがわかる中身のトークンで、バイト単位で過不足なく記録されること, so that 無編集の往復で同じバイト列を出し、編集した部分だけを作り直せる

#### Acceptance Criteria
1. When CommonMark の構文セットでパースした無編集の文書を検証する, the Amark Inline Parser shall 各葉の中身のすべてのバイトが、葉とその子孫の中身のトークンでちょうど 1 回ずつ覆われ、すべてのインラインのノードが自分のトークンを持ち、葉の中身が元の行のまま出せると判定される文書を作る
2. The Amark Inline Parser shall トークンの種類を `syntax-tree` の 9 種類に限り、テキストのトークンが NUL と不正な UTF-8 を含まないようにし（それらは置き換えのトークンにする）、タブの残りの空白をタブの残りのトークンにする
3. The Amark Inline Parser shall バックスラッシュのエスケープと文字参照を、エスケープと文字参照のトークンとして記録し、成立しない `\` と `&` をテキストのトークンとして記録する
4. The Amark Inline Parser shall 意味の値に入るバイトを、その値の項目を綴るトークンにし、区切り文字、括弧、引用符、取り除く空白を、項目を綴らない構造のトークン（役割の番号つき）にする
5. The Amark Inline Parser shall 表記の区別を style として記録する：強調と強い強調の区切り文字の文字、コードスパンのバッククォートの数と内側の空白の有無、ハードブレークの形、リンクと画像の形（インライン、完全参照、省略参照、ショートカット参照、オートリンク）、宛先の山括弧の有無、タイトルの引用符
6. The Amark Inline Parser shall 参照の形のリンクと画像について、ラベル（完全参照ではラベルを綴るトークン、省略参照とショートカット参照では記録した値）と形だけを記録し、宛先とタイトルを写さず、文書の定義の索引で解決されるようにする
7. The Amark Inline Parser shall ソフトブレークとハードブレークの前後の空白、ハードブレークの `\`、改行を、そのノードのトークンとして記録する
8. The Amark Inline Parser shall 組み込みの各インライン構文が使うトークンの種類、項目、役割の番号、style の対応を、記録の規約として公開し、利用者とレンダラが表記を区別できるようにする
9. The Amark Inline Parser shall 拡張のインライン構文も、組み込みと同じ方法で中身の上の位置にトークンを記録できるようにする
10. The Amark Inline Parser shall すべてのインラインのノードの構造を組み立ててから、トークンを記録し、記録が値の編集にならない（綴りを捨てた印を立てない）ようにする

### Requirement 9: エスケープに関わる文字の宣言
**Objective:** As a `markdown-renderer` の開発者, I want 構文セットのインライン構文が、テキストに現れると構文として解釈されうる文字を宣言し、それを問い合わせられること, so that 編集したテキストを書き戻すときに、拡張の構文を含めてエスケープを判断できる

#### Acceptance Criteria
1. The Amark Inline Parser shall インライン構文の拡張が、テキストに現れると構文の開始や区切りとして解釈されうる ASCII の文字を宣言できるようにし、きっかけの文字、区切り文字の文字、ブラケットの文字はその宣言に自動的に含める
2. The Amark Inline Parser shall 凍結した構文セットについて、宣言された文字の全体と、拡張ごとの宣言を問い合わせる手段を提供する
3. The Amark Inline Parser shall エスケープの方式（どの文脈でどの文字をエスケープするか）を決めず、宣言の情報だけを提供する

### Requirement 10: 自由な中身とインラインの断片
**Objective:** As a 木を編集するツールの開発者（msgstr の差し込み）, I want Markdown の断片をインラインとしてパースし、既存の葉の中身を置き換えるとき、完全なインラインの解析が使われること, so that 翻訳者が書いた強調やリンクを、その表記のまま木に反映できる

#### Acceptance Criteria
1. When 利用者が CommonMark の構文セットの文書で、葉を指定してインラインの断片をパースする, the Amark Inline Parser shall 断片を自由な中身としてこのエンジンで解析し、そのインラインの子とトークンで葉の中身を置き換えさせる
2. The Amark Inline Parser shall 自由な中身の改行（LF）と、改行の後の行頭の空白を、配置済みの中身の仮想の改行と同じ規則で扱い、ソフトブレークやハードブレークのトークンとして記録する
3. Where 利用者が挿入先の文書の定義を使うことを選ぶ, the Amark Inline Parser shall 断片の参照の形のリンクを、挿入先の文書の定義で成立するものとして解析する
4. When 断片で置き換えた葉を検証する, the Amark Inline Parser shall 置き換えた中身が、そのインラインのトークンでちょうど 1 回ずつ覆われ、ロスレス性の検証に通る文書にする

### Requirement 11: 限度、計算量、堅牢性
**Objective:** As a 信頼できない入力を扱う開発者, I want 病的なインラインの入力でも、解析の時間とメモリが入力の大きさにほぼ比例し、異常終了しないこと, so that サービスの中で安全にパースできる

#### Acceptance Criteria
1. The Amark Inline Parser shall 大量の区切り文字、開きだけや閉じだけの区切り文字とブラケット、深い入れ子の強調とブラケット、大量のバッククォート、閉じない生の HTML やオートリンク、大量の参照の形のリンクなどの病的な入力に対して、解析の時間が中身の大きさに対して二次以上にならないようにする
2. The Amark Inline Parser shall 深い入れ子の入力でも、再帰による呼び出しのスタックを使い果たさずに解析を終える
3. The Amark Inline Parser shall CommonMark spec が実装に許す制限（リンクの宛先の括弧の入れ子の深さ、ラベルの長さなど）を `block-parser` の走査の関数と同じ値で設け、spec の例をすべて満たす
4. If 中身に NUL や不正な UTF-8 が含まれる, then the Amark Inline Parser shall クラッシュせず、置き換えのトークンで綴り、意味の値では U+FFFD にして解析を続ける
5. The Amark Inline Parser shall 任意のバイト列と任意の区切りの逐次の入力に対して、クラッシュせず、リークせず、木の不変条件とロスレス性の検証を満たす文書を返すことを、ファジングと計算量のテストで確かめられるようにする
6. Where 開発者がテストを無効にしてファジングだけを有効にする, the Amark Inline Parser shall インラインのファジングのターゲットとそれがリンクする検証用のライブラリを、テストのフレームワーク（Naos）に依存せずに構成してビルドできるようにする

### Requirement 12: CommonMark spec の準拠テスト
**Objective:** As a Amark の開発者, I want 固定した版の CommonMark spec の全例が、パースと HTML 出力で期待どおりになり、綴りも正しいことを確かめるテストがあること, so that Amark が CommonMark に 100% 準拠し、無編集の往復の前提が成り立つことを継続的に保証できる

#### Acceptance Criteria
1. The Amark Inline Parser shall CommonMark spec 0.31.2 の全例を、例の番号の名前の付いたテストとして実行し、既定の CommonMark の構文セットでパースして生の HTML を許可した HTML 出力が、期待する HTML と一致することを確かめる
2. The Amark Inline Parser shall 準拠テストのすべての例で、木の不変条件、ロスレス性の検証、文書の根が元の表記のまま出せるという判定、逐次の入力と一括のパースの結果の一致もあわせて確かめる
3. The Amark Inline Parser shall 使う spec の版を 1 か所に固定し、spec のデータが固定した版と一致しなければ、テストの構成を失敗させる
4. The Amark Inline Parser shall spec のデータをテストデータとしてだけ扱い、そのライセンスと出典を明記し、ライブラリの成果物とソースのリリースのアーカイブに含めない
5. If spec のデータがない（ソースのリリースのアーカイブから構成した場合など）, then the Amark Inline Parser shall 構成とビルドとそれ以外のテストを成功させ、準拠テストを実行しなかったことを、合格と区別できる形で示す
6. Where 開発者が準拠テストを必須にすることを選ぶ（CI など）, the Amark Inline Parser shall spec のデータがないときに構成を失敗させる

### Requirement 13: 拡張 API の表現力の検証（GFM 相当）
**Objective:** As a 方言を実装する拡張の実装者, I want GFM 相当の構文が、公開 API だけで書いた小さな拡張の組み合わせで期待どおりに動くことが、テストで確かめられていること, so that 方言を拡張だけで完全に表現できると信頼できる

#### Acceptance Criteria
1. The Amark Inline Parser shall テストの中にだけ置くインライン側の検証用拡張として、取り消し線（新しい区切り文字）、拡張オートリンク（きっかけの文字を持たない構文）、脚注の参照（ブラケットの後処理と、ブロックの検証用の部品が作る脚注の定義の検索）を、公開 API だけで実装する
2. The Amark Inline Parser shall これらを、`block-parser` の検証用の部品（表、脚注の定義、タスクリスト）と `html-renderer` の検証用の部品（各構文の HTML、タグフィルタ）と CommonMark の構文セットに組み合わせ、表、取り消し線、タスクリスト、拡張オートリンク、タグフィルタ、脚注のそれぞれと、それらを混ぜた文書が、cmark-gfm と同じ形の HTML になることを、自前の代表的な入力で確かめる
3. The Amark Inline Parser shall 検証用拡張を組み合わせた文書でも、木の不変条件、ロスレス性の検証、元の表記のまま出せるという判定、逐次の入力と一括のパースの結果の一致を確かめる
4. The Amark Inline Parser shall 検証用拡張を配布するライブラリとインストールする成果物に含めない
5. The Amark Inline Parser shall 検証用拡張を書くために上流の公開 API に不足があれば、回避策を作らず、その API を持つ spec の変更として扱う
6. The Amark Inline Parser shall インラインの検証用拡張が記録するトークンの役割の番号とノード型を、検証用拡張のヘッダで公開し、他の spec の検証用の部品が同じ形を参照できるようにする

### Requirement 14: 検証
**Objective:** As a Amark の開発者, I want インラインの各構文とエンジンの振る舞いが、木のダンプとトークンで確かめられること, so that 準拠テストだけでは見えない綴りや API の誤りを見つけられる

#### Acceptance Criteria
1. The Amark Inline Parser shall インラインの構文ごとに、入力と期待する木のダンプ（トークンと style を含む）の組をデータとして書き、パースした結果と照合するテストを持つ
2. The Amark Inline Parser shall エンジンの API（構文の優先度、テキストのまとめ、区切り文字の種類の規則、ブラケットの後処理、きっかけの文字を持たない構文、文字の宣言、誤用の検出、失敗の伝播）を、テストの中だけの最小の構文で確かめるテストを持つ
3. The Amark Inline Parser shall インラインの解析を含むパースで確保が失敗したとき、メモリ不足が返りリークしないことを、確保の失敗の総当たりで確かめる
4. The Amark Inline Parser shall 例の区切りのデータから生成するテストの検査の関数（木のダンプの照合と HTML の照合）を提供し、`block-parser` の共有の生成手順で使えるようにし、他の spec が同じデータと同じ手順を使えるようにする
