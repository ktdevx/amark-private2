# Brief: syntax-tree

> 2026-11-26 改訂：構文木のモデルを「行 × 帯」と「中身の上の CST」に作り替える。入力資料はリポジトリの直下の `INPUT.md` である。requirements、design、tasks はこの brief と `INPUT.md` から作り直す。現行の設計との互換は保たない。

## Problem
Amark の利用者は、Markdown を意味のある構造（段落、見出し、強調、リンクなど）として参照・編集したい。主な用途は、Markdown と po の相互変換である。原文から msgid を抽出し、翻訳者が書いた msgstr を差し込んで、翻訳した Markdown を作る。このとき、次のことが要る。

- msgid を作者が書いた表記のまま作り、msgstr を翻訳者が書いた表記のまま出す（参照リンクを URL に展開しない、`_` を `*` に変えない）。
- 訳していない部分（コードブロック、表、HTML、参照の定義、空行、未翻訳の段落）を、原文とバイト単位で同じに出す。
- 引用やリストの中の段落を訳しても、コンテナの構造を崩さない。

Markdown のブロックは 2 次元である。コンテナ（引用、リスト項目）は各行の左端の帯で、中身はその右にある。インラインは、葉の中身から帯を除いて行をつないだ 1 次元の文字列の上にある。一般的な AST（cmark など）は元の表記を捨てるので往復できない。1 次元の CST や cmark ＋ trivia は、帯が葉の行の途中に割り込むので、きれいな部分木にならない。

## Current State
最初の設計による spec（tasks まで承認済み）と実装（`src/tree/`、`tests/tree/`）がある。この設計は、元の表記をソースの絶対位置の構文トークンとして各ノードに付け、編集を追跡する。持ち主の割り振り（帯はコンテナ、表記は葉、綴りはインライン）は正しいが、2 次元の構造を 1 本のトークンの列に平たくしているため、次の問題がある（`INPUT.md` の 1.3）。

- インラインのトークンがソースの絶対位置を指し、帯のトークンと入り混じる。markdown-renderer が、トークンの合流と接頭辞の探索で 2 次元の構造を組み立て直す必要がある。複数のソースが混ざる部分木では元の表記を使えない。
- 行が第一級でない。部分的なタブ（`PARTIAL_TAB`）と遅延継続（`LAZY_CONTINUATION`）が、トークンの特例として要る。
- 意味の値（属性とリテラルのコピー）と綴り（トークン）の両方を正として持つので、編集の追跡（`EDITED`、`STRUCTURE`、`RELOCATED` など）と祖先への伝播が要る。
- 参照リンクが定義の宛先をコピーして持つので、定義を変えても追従しない。表記の区別（`*` か `_` か）をトークンと役割の番号からしか取り出せない。タイトかどうかを、空行のトークンとは別の属性として持つ。

下流の spec（`block-parser`、`inline-parser`、`html-renderer`、`markdown-renderer`）には実装がない。

## Desired Outcome
- **配置の層**：文書が行の表（ソース、バイトの範囲、改行の種類、列の幅）を持つ。BOM は文書が持つ。コンテナは覆う行ごとに帯（`present` / `lazy`、項目の最初の行は `first`）と、自分が一番内側である空行を持つ。葉は行の範囲と、自身の表記（インデント、マーカー、フェンスの行、閉じの `###`、行末の空白）を、行と列の範囲で持つ。
- **綴りの層**：葉の中身は、帯と葉自身の表記を除いた残りを行の順に仮想の `\n` でつないだ文字列で、配置済み（元の行の列の範囲に対応する）か自由（自分のバイト列を持つ）の状態を持つ。インラインは中身の上の CST で、トークンは中身の上の位置だけを指す。中身がタブの途中から始まるときは `tab_remainder` のトークンで覆う。
- **3 つの情報の区別**：意味の値（value）は綴りがあれば綴りから導き、キャッシュする。表記の属性（style）は名前の付いた属性として持ち、値を編集しても残る。綴り（spelling）は元のバイト列そのもので、値を編集したノードは自分の綴りを捨てる。
- **参照リンク**：参照の形（full / collapsed / shortcut）のリンクと画像はラベルだけを持ち、宛先とタイトルは文書の定義の索引（文書の順で最初の定義）で解決する。定義の編集で索引を更新する。
- **リストのタイト**：空行から導く値とし、利用者が設定した値は上書きの値として持つ。
- **編集の状態は構造から導く**：綴りを持つか、帯を持つか、中身が配置済みで綴りが揃っているかで、元の表記を出せるかがわかる。編集の記録と祖先への伝播は廃止する。
- **ロスレス性の検証**：(1) 各行で、帯、空行の空白、葉自身の表記、中身の範囲が、行の列 `[0, 幅)` を重なりも抜けもなく分割していること、(2) インラインを持つ葉で、インラインのトークンが中身の全体を重なりも抜けもなく覆っていること、の 2 つの局所的な検査で行う。計算量は行の数とトークンの数に線形とする。
- **編集と取り込み**：中身の置き換え（msgstr の差し込み）、行の単位と中身の単位の複製と取り込み、ブロックの断片の行の表の取り込みを提供する。
- **位置の問い合わせ**：ブロックは行の範囲と列の範囲から、インラインは中身の上の位置を行と列に写して求める。
- 現行の spec の、構文トークンと編集の追跡に依存しない部分（レジストリ、構文拡張の記述子、構文セット、ノード型の記述子、文書とメモリの所有、走査、構造の編集の規則、比較、S 式のダンプ）は、新しいモデルに合わせて引き継ぐ。

## Approach
- `INPUT.md` の 2 章（理想形の概要）と 4 章（詳細な設計の方針）のモデルに、部分的な取り入れではなく完全に移す。
- 現行の requirements の 1〜10 を、`INPUT.md` の 6.3 の表に沿って改訂する。要件 6（構文トークン）は全面的に書き換え、要件 7（編集の追跡）は廃止して、綴りと帯の有無を問い合わせる API に置き換える。新しく、定義の索引、中身の状態と置き換え、style の取得と設定（未設定の状態を含む）の要件を足す。
- ノード型の記述子に、style の項目（名前、種類：文字 / 整数 / 列挙 / 真偽、既定の値）の宣言を足す。拡張のノード型も同じ仕組みで style を宣言する。
- `src/tree/` は新しいモデルで作り直す。流用する部分（レジストリ、構文セット、ノードの中核、走査、ダンプなど）と作り直す部分は、design で決める。
- `INPUT.md` の 8 章の未決定事項は、この spec の requirements と design で決める。特に、Q8（綴りを捨てる単位）と Q11（GFM の表）は、モデルの形に関わるので requirements の段階で決める。

## Scope
- **In**：
  - 文書とメモリの所有、ソースの保持、行の表（逐次の入力での末尾への追加を含む）
  - 組み込みのノード型と、その value と style（`INPUT.md` の 4.6）
  - 配置の層（帯、空行、葉自身の表記）と綴りの層（中身、インラインのトークン）の記録・参照の仕組み
  - 意味の値の導出とキャッシュ、style の取得と設定
  - 定義の索引と参照の解決
  - 参照、走査、構造と内容の編集、中身の置き換え、複製、別の文書からの取り込み
  - ロスレス性の検証（行ごとの分割と中身の被覆）
  - 綴りと帯の有無の問い合わせ
  - ノード型の登録（style の項目の宣言を含む）、構文拡張の記述子、構文セット
  - 木の比較（style を含めるかを選べる）、S 式のダンプ（行、帯、中身、綴り、style を含められる）、テスト用に S 式から木を組み立てる補助
- **Out**：
  - パースの処理と、表記を実際に記録する処理（`block-parser`、`inline-parser`）
  - HTML と Markdown の出力の処理、帯と表記の合成、エスケープ（`html-renderer`、`markdown-renderer`）

## Boundary Candidates
- 配置の層（行の表、帯、空行、葉自身の表記）：パーサが作り、Markdown レンダラが使う
- 綴りの層（中身、インラインのトークン、value の導出）：インラインのパーサが作り、両方のレンダラと利用者が使う
- 意味の面（型、子、value、style、定義の索引）：利用者が読み書きする API
- 拡張のレジストリ（すべてのスロットの土台）

## Out of Boundary
- ブロックやインラインの構文規則、HTML や Markdown の出力規則
- 書き戻しで帯と綴りを合成する処理（`markdown-renderer` が持つ）。ただし、合成に必要な情報（どこに綴りと帯が残っているか、style）は、ここで提供する。
- msgid の空白の正規化を、ライブラリの機能にするか（Q5）は、po の用途の API として別に決める。この spec では、中身を取り出す API を提供するところまでとする。

## Upstream / Downstream
- **Upstream**：`foundation`（`AMARK_ERROR_NOT_LOSSLESS` は意味を変えずに使う）
- **Downstream**：`html-renderer`、`block-parser`、`inline-parser`、`markdown-renderer`、利用者の拡張。どれも、この spec の改訂の後に改訂する（`roadmap.md` の Existing Spec Updates）。

## Existing Spec Touchpoints
- **Extends**：`syntax-tree`（この spec 自身の作り直し）
- **Adjacent**：`block-parser` と `inline-parser`（配置と綴りを記録する側）、`markdown-renderer`（それを使って書き戻す側）、`html-renderer`（位置とリンクの値を問い合わせる側）

## Constraints
- 新しいモデルは、次の CommonMark 特有の要素を、特例のトークンなしで表せなければならない。
  - コンテナの帯（`>`、リストのマーカーとインデント）と、空行での帯
  - 遅延継続行（`lazy` の帯）
  - 部分的なタブ（列の範囲で分ける。範囲の境界をタブ以外の文字の途中に置かない）
  - 改行の種類（LF、CRLF、CR）と、行末に改行のない最後の行
  - NUL 文字と不正な UTF-8 の置き換え（中身の `replaced` のトークン）
  - BOM（文書が持つ）
  - エスケープと文字参照の元の表記
- 木の不変条件として、兄弟のブロックは同じ行を共有しない。ただし、GFM の表のように 1 つの行を複数のブロックで分け合う構文を拡張で表せることを確かめ、必要ならこの条件を改める（Q11）。steering は、GFM 相当の構文を拡張だけで実装できることを約束している。
- 意味の値を遅延して計算しキャッシュするので、1 つの文書を複数のスレッドで同時に読めるかを決めて明記する（Q12）。
- 公開型は不透明型とし、ABI の安定を意識する。
- 下流の spec が表記の記録やスロットを足すとき、モデルやレジストリの設計に問題が見つかったら、この spec に戻って更新する。
