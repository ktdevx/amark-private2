# Brief: syntax-tree

## Problem
Amark の利用者は、Markdown を意味のある構造（段落、見出し、強調、リンクなど）として参照・編集したい。主な用途の 1 つは、組み込み側で翻訳のためにテキストを置換することである。その際、編集していない部分は元の表記のまま残り、編集した部分だけが変わってほしい。一般的な AST（cmark など）は元の表記を捨ててしまうため、往復で同じ出力を得られない。逆に完全な CST は、具象構文を意識しないと編集できないため扱いにくい。

## Current State
まだ存在しない。`foundation` が用意する共通ランタイム（アロケータ、バッファ、エラー）の上に作る。

## Desired Outcome
- 意味単位のノードを持つ木を作り、参照し、走査し、編集できる。
  - 走査：イテレータ（入る/出るイベント）
  - 編集：挿入、削除、移動、置換、テキストやリテラルの変更、属性の変更
- 各ノードは、元の表記を構文トークンとして持てる。構文トークンは、ソース範囲の参照、マーカー、空白、コンテナの接頭辞などを表す。
- 編集が追跡され、`markdown-renderer` が「どのノードを元のまま出し、どのノードを作り直すか」を判断できる。
- ノード型は拡張から登録できる。CommonMark の組み込みのノード型も同じ仕組みで登録する。
- 構文拡張のレジストリと構文セット（拡張の組み合わせ）の土台がある。パーサやレンダラは、ここにそれぞれのスロットを足していく。

## Approach
- 不透明型の `amark_node` と、アリーナまたはドキュメント単位のメモリ管理を基本にする。ノードを削除したときの所有権の規約は design で決める。
- 拡張の情報は、組み込みノードも拡張ノードも同じ形で持つ。具体的には、ノード型 ID、ノード型ごとのデータ（見出しのレベル、リンク先、表の配置など）、型ごとの関数表（解放、複製、比較）を用意する。
- 構文トークンは、元のソースバッファへの範囲参照を基本にする。木が元のソースを保持する（または共有する）ことで、元のバイト列をそのまま出力できるようにする。
- 編集済みの追跡は、ノード単位のフラグ（自身が編集されたか、子孫が編集されたか）を基本にする。テキストを部分的に置換したときの粒度は design で決める。
- 構文拡張の記述子（`amark_extension`）は、名前、ノード型の登録、各スロットへのポインタをまとめた単位とする。構文セットは、記述子を順序付きで組み合わせたものとする。組み込み構文を無効化したり置き換えたりできるようにする。各スロットの具体的なインタフェースは、そのスロットを実行する spec が定義する。

## Scope
- **In**：
  - ノードモデル、組み込みノード型の定義（CommonMark の全ノード：document, block_quote, list, item, code_block, html_block, paragraph, heading, thematic_break, text, softbreak, linebreak, code, html_inline, emph, strong, link, image）
  - 構文トークンのモデル
  - 走査と編集の API、編集済みの追跡
  - ノード型の登録 API、拡張の記述子と構文セットの土台
  - デバッグ用の木のダンプ（テストで使う S 式などの形式）
- **Out**：
  - パースの処理、レンダリングの処理（それぞれのスロットの中身）

## Boundary Candidates
- ノードモデルと編集 API（利用者が直接使う API）
- 構文トークンのモデル（パーサが作り、Markdown レンダラが使う）
- 拡張のレジストリ（すべてのスロットの土台）

## Out of Boundary
- ブロックやインラインの構文規則、HTML や Markdown の出力規則
- 編集したノードを Markdown に作り直す処理（`markdown-renderer` が持つ）。ただし、作り直しに必要な情報（何が編集されたか）は、ここで提供する。

## Upstream / Downstream
- **Upstream**：`foundation`
- **Downstream**：`html-renderer`、`block-parser`、`inline-parser`、`markdown-renderer`、利用者の拡張

## Existing Spec Touchpoints
- **Extends**：なし
- **Adjacent**：`block-parser` と `inline-parser`（構文トークンを作る側）、`markdown-renderer`（構文トークンを使う側）

## Constraints
- 構文トークンのモデルは、次の CommonMark 特有の要素を表現できなければならない。design では、`block-parser` と `markdown-renderer` の要求を先取りして検討する。
  - コンテナの接頭辞（`>`、リストのインデント）
  - 遅延継続行
  - タブの部分展開
  - 改行コードの違い（LF、CRLF、CR）
  - NUL 文字の置換
  - BOM
  - エスケープや文字参照の元の表記
- 公開型は不透明型とし、ABI の安定を意識する。
- 後続の spec がスロットを足すとき、レジストリの設計に問題が見つかったら、この spec に戻って更新する。
